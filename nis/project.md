# Описание проекта

## Назначенное задание

[P09-A. FoundationDB: транзакции и отказы](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p09-a-foundationdb-transactions.md)

## Выбранный технический путь

Авторский артефакт: готовый выпуск FoundationDB 8.0.0 как объект измерения и собственный
код поверх него (генератор нагрузки, журнал, чекер). Ревизия из задания
`apple/foundationdb@ddec61a629a9` входит в выпуск 8.0.0: GitHub compare дает
`ahead_by: 441, behind_by: 0`. Поэтому сборка из исходников не нужна, кластер поднимается из
официального образа `foundationdb/foundationdb:8.0.0`, а Go-биндинги и `libfdb_c` взяты той же
версии. Simulation tests из исходников в обязательный объем не входят.

## Что будет сделано и как это проверить

### Кластер, нагрузка и журнал (роль A)

1. **Локальный кластер** из пяти процессов `fdbserver`, по одному на контейнер, в режиме
   `double ssd` с тремя координаторами ([docker-compose.yml](../cluster/docker-compose.yml)).
   Как проверить: `scripts/cluster-up.sh` и `scripts/roles.sh` показывают 5 процессов в
   5 зонах, `Fault Tolerance - 1 machines`, состояние `fully_recovered`.
2. **Генератор нагрузки с управляемой конфликтностью** ([cmd/loadgen](../cmd/loadgen/main.go)).
   Каждая транзакция читает `k` ключей из горячего множества размера `H` и пишет в них
   значение, уникальное для попытки; конфликтность задается `H`.
   Как проверить: тесты из [docs/DESIGN.md](../docs/DESIGN.md) проходят в `make check`; на
   пробном замере доля конфликтов растет при уменьшении `H`
   ([сводка](../results/checks/trial-summary.txt)).
3. **Журнал исходов**: одна строка JSONL на каждую попытку с версиями, прочитанными и
   записанными значениями, исходом и кодом ошибки FDB.
   Как проверить: тест `TestJournal_RoundTrip`; журнал читается чекером роли C.
4. **Финальное чтение горячих ключей** после окончания нагрузки, нужно чекеру для проверки
   сохранности (запрос роли C).
   Как проверить: в конце журнала есть запись финального состояния всех `H` ключей.
5. **Работа генератора во время отказа**: попытки, оборванные отказом, получают исход
   `unknown` или `aborted` по коду ошибки, генератор продолжает нагрузку после
   восстановления.
   Как проверить: прогон с отказом процесса завершается без ошибки генератора, в журнале
   есть попытки с исходом `unknown`.

[Роль B: серии запусков, внедрение отказа, метрики, отчет.]

### Проверка сериализуемости и сохранности (роль C)

1. **Чекер сериализуемости по журналу исходов** (`cmd/checker`). Строит по журналу граф
   зависимостей между подтвержденными транзакциями и ищет в нем циклы; на выходе число и
   типы нарушений с примерами транзакций.
   Как проверить: тесты на эталонных историях с известным ответом проходят (`make check`);
   на журнале snapshot-прогона чекер находит нарушения, на журналах штатных прогонов
   не находит.
2. **Проверка сохранности подтвержденных записей.** По журналу и финальному чтению горячих
   ключей проверяется, что каждая запись с исходом `committed` осталась в истории ключа и не
   была потеряна, в том числе после отказа процесса.
   Как проверить: тест на истории с удаленной подтвержденной записью дает ошибку; на
   каждом прогоне с отказом в отчете приведено число потерянных подтвержденных записей.
3. **Перекрестная проверка вторым способом.** Независимая проверка по версиям FDB
   (`read_version`, `commit_version`), не использующая граф зависимостей. Оба способа
   запускаются на каждом журнале, их вердикты должны совпадать.
   Как проверить: в сводке по сериям есть столбцы вердиктов обоих способов; расхождение
   разбирается в отчете как ошибка одного из чекеров.
4. **Проверка самого чекера.** Эталонные истории и журналы с внесенными искажениями
   (подмена прочитанного значения, удаление подтвержденной записи), которые чекер обязан
   отвергнуть.
   Как проверить: каждое искажение покрыто тестом, тесты входят в `make check`.

## Поддерживаемые сценарии

Нагрузка (роль A): 8 клиентов параллельно выполняют транзакции «прочитать `k = 4` ключа
и записать в них новое значение» в течение заданного времени. Ключи выбираются равномерно
из горячего множества размера `H` генератором с фиксированным seed. Перед прогоном диапазон
ключей очищается. Ожидаемое поведение: при меньшем `H` растут доля конфликтов, число повторов
и хвостовая задержка, подтвержденные транзакции остаются сериализуемыми.

[Роль B: сценарий отказа.]

Со стороны проверки (роль C): каждый журнал штатного прогона и прогона с отказом проходит
обе проверки. Ожидаемое поведение: 0 нарушений сериализуемости и 0 потерянных
подтвержденных записей. Попытки с исходом `unknown` (например, 1021 при отказе) допускаются
в обоих вариантах: записи применены или не применены. Snapshot-прогон служит
контрольным случаем, в котором нарушения обязаны найтись.

## Упрощения

Упрощения кластера и нагрузки (роль A):

- Все процессы работают на одном ноутбуке, «машины» заменены контейнерами с разными
  `zoneid`. Сетевых задержек и отказов дисков между машинами нет, поэтому время
  восстановления и задержки меньше, чем в распределенном кластере, и переносить их на
  производственный масштаб нельзя.
- Данные хранятся в двух копиях (`double`), поэтому кластер переживает отказ ровно одного
  процесса; проверяется именно такой отказ, как в задании.
- Нагрузка синтетическая: одинаковый размер транзакций, равномерный выбор ключей. Вывод
  относится к этой нагрузке.
- Таймаут ограничивает одну попытку (5 с), после 1031 транзакция начинается заново;
  backoff между повторами оставлен как в клиенте FDB по умолчанию.

[Роль B: упрощения эксперимента.]

Упрощения проверки (роль C):

- Чекер рассчитан на нагрузку генератора: каждая транзакция читает свои ключи и пишет в
  каждый из них уникальное значение. Благодаря этому порядок версий каждого ключа
  восстанавливается из журнала однозначно, и проверка выполняется за линейное время. Для
  произвольных транзакций такой чекер не подходит.
- Проверяется сериализуемость, а не строгая сериализуемость: порядок в реальном времени
  дополнительно сверяется только во втором способе через версии FDB.
- Если запись с исходом `unknown` нигде не прочитана и не видна в финальном состоянии,
  считается, что она не применена. Исход `unknown` разрешает оба варианта, а этот
  вариант согласуется со всеми наблюдениями, поэтому ложного нарушения он не создает.
